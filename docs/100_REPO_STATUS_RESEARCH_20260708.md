# 100 个新 repo 的当前情况

这份文档只讨论 **Goal B 的 100 个新 repo**，不把 MLS-Bench 原有 67 个 repo 混进来。历史记录和 memory 只作为证据来源；正文不按历史记录组织，也不保留抽象 onboarding 分层。

## 我们现在在做什么

当前工作是把 **MLS-Bench 之外新增的 100 个 repo** 变成可验收的 MLS-Bench 任务集，而不是继续整理 MLS-Bench 原有 67 个 repo，也不是清理另一批 `.fleet_todo.json` 里的旧 fleet repo。

对每个新增 repo，需要完成三件事：

1. **造题/扩题**：扩展到 `>=10` 个有明确研究问题的 tasks/questions；如果最终少于 10 个，要写清楚 honest drop / frozen scope / 仍需继续扩展，不能用含糊状态带过。
2. **跑 anchors**：每个 task/question 都要有真实 measured anchors/leaderboard；需要使用真实数据和真实/原生 scale，不能为了方便把任务缩成 toy。
3. **验收并上 Mangrove**：anchors 通过后，要确认这些 baseline 分数能用于当前 task 的 score 范围校准，再整理 Harbor 格式和 image，放到 Mangrove strict 口径下验证或登记。

## 接着往下做要注意什么

1. **真实数据优先**：任务语义要求真实数据/真实 benchmark 时，必须使用真实数据；不能把应该真实数据的任务替换成 synthetic toy data。只有任务本身就是算法玩具、合成基准或明确声明为 synthetic scaffold 时，才可接受合成数据。
2. **真实 scale 优先**：anchor 要尽量保持真实/原生 scale。只要总规模低于约 `50 H20 hours`，就不应该把训练轮数、数据量、分辨率、序列长度等缩到失真。
3. **anchors 主要用于评分范围校准**：anchor 的目的不是证明某个 RQ 的科学结论，而是让我们知道当前 task 的 baseline 分数大概落在哪个范围，方便设计和校准 score。只要 anchor 是在真实数据/合理 scale 上跑出来的、能代表该 task 的 baseline 分数范围即可；不需要为了每个 RQ 额外证明 baseline 排序或机制解释。
4. **同 repo 的 RQ 可以共享 anchors**：同一个 repo 下不同 research questions 可以共享同一组真实跑出来的 anchors/leaderboard，只要这组结果能给这些 task 的评分范围提供参考。不能共享的是没有真实运行依据的占位 rows、明显和当前 task 分布/metric 不相关的 rows，或 synthetic/toy scale 结果冒充真实 scale anchors。
5. **先补短板，再上 strict**：`<10` 的 repo 先补 questions 或写清 drop/frozen accounting；已经 `>=10` 但未 strict 的 repo，优先核真实数据/scale、补 anchors 的分数范围证据、整理 Harbor image，再跑或登记 Mangrove strict。
6. **不要混入别的 repo 集合**：`BasicTS`、`gptq`、`flash-attention`、`Neural-Solver-Library`、`LLaDA`、`imitation`、`omnisafe`、`epymarl`、`humanoid-gym`、`tdmpc2` 等可能出现在其它 fleet/Mangrove 记录里，但不属于这份 100 新 repo 表；不要直接算进这里。

下表里的 `remaining work` 就是当前行动清单：`<10` 的先补 questions 或写清 drop/frozen accounting；`>=10` 但未 strict 的要核真实数据/scale、补/复核 anchors、再做 Harbor/Mangrove；已经 Mangrove Done 的只需后续维护证据一致性。

## 字段说明

- `tasks/questions`：当前 config 中能数到的 task/question 数；`>=10` 表示已达到扩展目标，`<10` 表示还需要扩展或补 honest drop/frozen accounting。
- `anchors/data evidence`：目前是否有真实数据、原生 scale、leaderboard/mlaunch/fleet/Mangrove 相关证据；有证据不等于已通过 strict。
- `Mangrove`：是否已经能映射为 Mangrove strict Done。
- `remaining work`：下一步必须做什么，尤其是补到 `>=10 questions`、核真实数据/scale、跑 anchors、整理 Harbor image、登记 Mangrove strict。
- `runtime evidence`：本表旧行大多只是历史 task 的 verifier 墙钟，不能据此判断 real scale。只有明确写出 terminal task/container、完整 workload、GPU、setup/agent/verifier/trial/platform 分解的行才是当前终态实测；当前 accepted repo 的统一终态口径见后文 `2026-07-11 Real-Scale Runtime Ledger`。Config 的 `time`/timeout 是失败保护上限，不是实际耗时。

## 当前行动分桶

- **先补扩展或 drop/frozen accounting**：当前 `<10` 或 shipped/drop 数量未交代清楚的 repo，先补到 `>=10` questions；如果不能补，必须写清 honest drop / frozen scope，而不是用模糊状态带过。
- **再复核 anchors 和 strict**：已经 `>=10` 但未计 Mangrove strict Done 的 repo，重点核真实数据、真实/原生 scale，以及 anchors 是否足以给当前 task 的 baseline 分数范围做 score 校准，然后整理 Harbor image 并跑/登记 Mangrove strict。
- **fleet verified 不是终点**：有 fleet verified 的 repo 只说明本地或 fleet 层面已有可用证据；仍要按本文件口径补 Harbor/Mangrove strict，并复核是否存在 synthetic/scale 风险。

### 验收规则

1. **Agent 与 verifier 分开判断。** Agent 失败、nop、零编辑都可以；此时 verifier 应评测未修改的 native solution。Agent 失败不自动归零，也不代表 agent 获得了 native 分数。
2. **Verifier 必须 fail closed。** 任一配置或 seed 缺失、命令 `rc != 0`、parser 失败、训练/评测未到最终 completion proof、metric 缺失或 NaN/Inf、artifact 不完整，都必须得到精确 `0.0`。禁止写死正分、fallback metric、伪造 leaderboard row 或把分数注入给 verifier 读取。
3. **所有 setting 都计分。** `public` / `hidden` 只是历史展示标签，不影响是否计分，也不应出现在 agent instruction 中。当前 accepted task 的每个配置和 seed 都是 required，并参与最终聚合。
4. **Baseline 定义。** `native` 是 agent 不修改 workspace 时实际运行的 solution；`strong` 是同一数据、同一模型、同一预算下实测的校准参考编辑。Strong row 不能由预测值、手写常量或不同规模的旧实验代替。QA 的当前 score 是 baseline-free official F1 映射，因此单独标注。
5. **Real scale 不能由墙钟时间反推。** 训练任务必须对齐 upstream/community 的数据量、steps/epochs/tokens、分辨率和序列长度；完整 canonical-split inference 可以在数分钟内结束。短成功不自动失败，长任务也不自动通过。
6. **运行环境。** 最终 verification 使用一个按 digest 固定、依赖/模型/数据预装的 repo image；per-task build 只允许存在性检查、`rm` 和 `COPY _scaffold` 一类文件操作，不在 verification 中执行 `pip`、`apt`、`conda`、模型下载或编译。最终 Mangrove 每个 task 当前使用 1×H20 串行执行，且任何 task 最多 4 GPU。
7. **Representative 只共享 runtime 证据，不豁免 sibling 修复。** 一个完整 representative 可以证明该 repo 在真实 scale 下的实测耗时，不要求把昂贵评测机械重复十次；其余 siblings 可以只做静态修复和验证，且 task-specific scaffold/template/edit surface、parser/spec 或 setting 可以不同。但 repo-level protocol/scale correction、data/model/image pins、completion contract、fail-closed、所有 setting/seed、资源上限和 instruction 清理必须传播，并逐 task 证明自身闭合。若后续修复只改 parser/scorer/proof/instruction，未改变 representative 的模型、数据、steps、分辨率或实际 workload path，已有 terminal runtime 可以继续使用；只有这些 material workload 项改变时才重跑 representative。任何一个 sibling 仍使用旧实现，整个 repo 都不能标 `SHIPPED`。

### Runtime 的读法

- `environment setup`：Mangrove 拉取/解压 pinned image、做 per-task `rm + COPY`、启动容器的时间。冷缓存时它可能比 verifier 长很多，但不属于训练/推理 workload。
- `agent`：nop 或被评测 agent 的实际执行时间。nop 只保留 native workspace，不能当 Oracle。
- `verifier`：真正执行所有 required setting、解析指标并计算 reward 的时间。判断 scale 时主要看这一段及其内部 completion proof。
- `total wall`：Mangrove container 的 `started_at -> finished_at`，近似 `setup + agent + verifier + framework overhead`。从 batch 提交到 container 启动的排队/dispatch wait 另算，不属于 compute。
